# Inactive private delivery backend

20 October 2026. Local current-main integration of the independently reviewed Lane A R2 and Lane B R2 source, based on `f3900766a8546fb1c23d107cf8a8e1c9cf12f9b9`. The signed receiver is present but inactive by default. No production migration, provider setting, secret, deployment or activation is included. This backend trusts only private service-binding callers. The receiver authenticates the original raw bounded webhook before calling it. See `email-delivery-webhook-runbook.md` for activation prerequisites and the current integration audit for fresh evidence.

The exact three reviewed reducer files are copied unchanged. The reducer's original documentation remains a record of that offline tranche; it does not claim this new integration was reviewed. New integration evidence belongs in this runbook and the audit report.

`server/mail-recipient.mjs` exports `recipientBinding(providerMessageId,envelope)`. It returns null unless the actual outgoing message has exactly one bare ASCII mailbox in `to` and absent/empty `cc` and `bcc`. Its restricted subset refuses display names, Unicode, surrounding whitespace and malformed domain labels rather than guessing. A successful binding contains only `recipientCount:1` and a lowercase hexadecimal SHA-256 digest of UTF-8 `JSON.stringify(['cv-recipient-v1',exactMessageId,localPart+'@'+lowercaseDomain])`. Local-part case stays unchanged. This is pseudonymous personal data with the source receipt's original expiry, not anonymized data. It has no network, clock, logging, storage, secrets or Node-specific dependencies.

The private POST `/mail-delivery/observe` accepts exactly `providerMessageId`, `source:'webhook'`, fixed `type`, verified transport `eventId`, `occurredAt`, `checkedAt`, `recipientCount:1` and `recipientDigest`. Times are positive safe-integer Unix seconds, event time no later than check time and check time no later than server time. The later adapter must use the signed envelope's event timestamp and verified Svix ID. It must not pass recipient addresses, subject, content, headers, diagnostics or tags. The backend derives purpose/reference/attempt from exactly one authoritative source globally, rather than trusting caller-selected association. Manual-check capture is not implemented.

A 200 response contains only `{ok:true,disposition,reason}`. Fixed dispositions are `applied`, `duplicate`, `ignored`. Reasons are `receipt-unavailable`, `binding-unavailable`, `event-conflict`, `snapshot-unavailable`, `observation-unavailable`, `original-expiry`, `duplicate-event`, `observation-recorded`. Malformed input is400, oversized internal projection413 and transient failure/contention503. An uncertain database acknowledgement returns503 even if a later replay discovers the commit succeeded. No route sends email or creates retry authority.

The additive0012 migration supplies two evidence tables, source and assertion views, indexes and cleanup triggers. It has no backfill. Existing accepted receipt fields remain authoritative. Initial capture only accompanies the first new accepted mark; an old or legacy success cannot acquire a fabricated binding on replay. Manual capture uses the exact accepted reservation. Existing expired-artwork manual sends still record their ordinary accepted history and retain no new provider ID or binding. Record-disabled initial sends keep working with no invented Orders link. Duplicate provider IDs may still be recorded as truthful acceptance, while delivery correlation fails closed globally.

New initial Orders links are established only through the existing server create/match flow, after exact fingerprint checks and before initial sent flags, with an unset-or-identical unique link. A failed association rolls back a newly inserted order. Existing linked retries remain compatible. Historical unlinked successes receive no guessed association. Their exact already-existing order may still recover through the public sender without assigning a link: the private transaction revalidates order/submission identity, fingerprint, exact snapshot, original live deadlines and absence of a competing link. Already accepted mail gains no binding; a first later successful customer receipt may capture its own normal binding with no guessed Orders association. This exception is unavailable to new-order creation. No contact lookup, display-reference lookup or HMAC reconstruction is used.

Observation persistence uses primary sessions where D1 exposes them, an initial authoritative read, the immutable reducer, and a maximum of three revision-CAS attempts. The SQL write rechecks global source cardinality, exact accepted tuple, binding, original expiry and event ownership. Snapshot and bounded unique event claims share a transactional batch. A final SQL assertion view backed by an abort trigger rechecks original database-time expiry/source and every retained event claim. It aborts the entire batch on failure. No-op replays also pass the same guarded persistence boundary; their evidence does not change, while the private concurrency revision may advance. The revision and operation token are never projected or used to renew retention.

Private order detail adds `mailDelivery` summaries containing purpose, attempt, acceptance/original-expiry times, fixed state/reason, complaint flag and nullable `source`, `checkedAt`, `occurredAt`. These extra facts are a read-only integration addition to the reviewed Lane A projection. `source` identifies retained evidence only when every reducer-validated observation shares `webhook` or `manual-check`; it is not an inferred terminal provenance. `checkedAt` is the maximum trusted retained check time, never the current request time or acceptance time. `occurredAt` is available only for an ordinary state/reason with an exact supporting event type and one agreeing positive event timestamp across all matching observations. It stays null for absent evidence, mixed sources, differing matching event times, complaints, review/conflict/capacity states or status-only checks. Initialized receipt bindings have all three values null. There is no manual-check capture path. The summary excludes provider IDs, HMAC source references, recipient digests and event ledgers. Existing released manual receipt fields retain their prior policy. List/public APIs and customer responses gain no delivery fields. Detail reads use the existing read-only transient retry helper; writes are never blindly replayed.

Initial evidence expires with the original two-day submission deadline. Manual evidence expires with the original artwork deadline, normally fourteen days. Readers hide evidence at expiry regardless of cleanup lag. Existing hourly cleanup deletes expired/orphan state and event claims; source deletion/scrub triggers also remove auxiliary data. Reduced order/attempt history keeps its existing six-calendar-month policy. No stage, proof, fulfilled/reopen action, check or new event restarts the earlier evidence deadline.

Verification uses synthetic recipients/providers and isolated SQLite fixtures. It covers actual acceptance payloads, record-disabled paths, manual expiry and old-caller compatibility; domain/local case and Worker-like standard-Web-Crypto execution; all receipt purposes and exact manual attempts; replay/terminal/complaint/capacity behavior; source/cardinality mutation after read, concurrent outcomes, bounded CAS misses, binding/claim failure rollback, final SQL clock crossing and lost commit acknowledgement; PII projection exclusion and zero external fetch. Worker-like VM execution and a successful browser-platform security bundle are compatibility checks, not live Cloudflare/D1 execution or concurrency acceptance.

Keep website and separate admin gates, payments off, manual Preview/Send, all quotas and duplicate-send protections unchanged. Initial same-key recovery remains the released behavior. This code does not solve the external provider-acceptance/D1 gap.

# Initial order email design previews

21 October 2026. Implemented locally under the existing Founders Hub task “Improve order emails with design previews”. Publication and actual inbox acceptance remain separate. No real email was sent during implementation.

Initial customer and owner messages reuse the existing shared design, reference, truthful Unpaid wording and next steps. Both receive the same small labelled JPEG contact sheets: one per item, assembled puzzle layouts, all selected collection faces, and the already prepared photo/Business/Handy/game artwork. Labels retain set counts and exact multiplied selected-design copies. They are display previews, never print artwork or an approval request. Manual status emails and all artwork revision/preparation controls are unchanged.

The browser processes prepared chosen artwork sequentially and keeps previews only in the in-memory submission attempt. A 160-pixel square uses bounded JPEG quality attempts. Failure to produce a small preview leaves the normal order available. Limit: 12 item previews, 5,000 base64 characters each, 60,000 total. More items remain orderable; missing previews are disclosed while the order summary remains present. This is an email display budget, not a new order or magnet cap.

Before the attempt is frozen, UTF-8 JSON measurement includes the complete payload and conservative reserves for the maximum current Turnstile value, signed grant/resume tokens and envelope overhead. Preview fields are removed from the end until the reserved request fits the existing 150,000-byte limit. Retries reuse the exact frozen payload, signed fingerprint and provider idempotency keys. Optional preview version/fields are absent on legacy requests, preserving their established email payloads and fingerprints.

The server validates at most 12 baseline JPEGs with 64 to 160 pixel square edges, strict byte/total bounds and no EXIF/comments/progressive/trailing content. It performs bounded marker checks, not image decoding or paid image transformation. Previews travel as inline `content_id` JPEG attachments in the existing direct HTML/text/attachments API payload. [Resend documents CID embedding](https://resend.com/changelog/embed-images-using-cid). No public image URLs, remote image fetches, new sending endpoint or hosted-template variable contract is introduced. The attachment MIME type and filename remain explicit.

`orderRecord` deliberately excludes preview version and image fields. R2 retains only the existing full print artwork. No database migration, thumbnail object, expiry extension, provider setting, quota increase or paid feature is added. The existing 14-day artwork/request expiry and six-month reduced order history remain. Checkout/consent and privacy copy disclose that already sent small previews follow provider and mailbox retention; private-artwork expiry does not delete email copies. Original photos and unsent drafts remain in browser memory. Mailbox deletion policy remains a separate existing owner task.

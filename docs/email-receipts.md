# Accepted email receipt metadata

This is partial TECH-03 observability. A validated Resend accepted ID is provider acceptance evidence only. It does not establish delivery, mailbox receipt, rendering, bounce/suppression status or reply routing. No provider event pipeline or reconciliation is enabled.

Initial owner and customer receipt IDs are stored in separate nullable `submissions` columns with server recording timestamps. The existing opaque submission key supplies the reference and the fixed owner/customer columns supply purpose. Manual updates store ID/time on the exact existing `order_update_attempts` reservation; its order/version/status and fixed `manual-update` purpose identify the operation. Authenticated order detail may return those fields. No customer content, raw provider response, new logs or public receipt ID is added.

IDs accept 1 to 128 ASCII letters, digits, underscore or hyphen. Malformed IDs do not count as accepted responses. Success flags and initial metadata share one statement. Manual state and receipt metadata use the existing atomic outcome transaction and attempt identity, preserving late-mark, retry and Fulfilled safeguards. Legacy marks without IDs remain compatible and leave unknown metadata null; migration does not fabricate historical receipts.

Apply additive migration `0011_mail_receipt_metadata.sql` only after PR14's `0010_manual_update_attempts.sql`, through the normal reviewed release process. No live migration or publication is part of this work. Deploy compatible private Security and initial/admin senders in order, with required current-head CI and protected release checks. Keep the additive columns on rollback; an older caller can keep marking without receipt IDs. Keep the new Security receipt-expiry cleanup during sender/UI rollback; do not roll back to a private worker lacking that cleanup while receipt metadata remains. Use a compatible forward repair. Do not remove PR14's attempt-aware writer after retry history exists. New sender/private-service versions must be coordinated before claiming metadata persistence is available.

The pre-existing opaque submission retry row expires after two days, so its nullable receipt fields expire with that row. This is separate from the fourteen-day artwork/request deadline and longer order/attempt history. New manual provider ID/time fields are hidden immediately at the original artwork deadline and cleared by existing hourly cleanup; later manual updates still send normally but do not retain those new fields. Their deadline never restarts. Existing attempt state/history, original artwork expiry and order retention are unchanged. This slice does not approve or verify the overall retention policy; TECH18 and owner policy reconciliation remain separate.

Initial-send idempotency/retry semantics remain unchanged, including the existing503 customer-receipt retry behavior and stable provider idempotency keys. A provider acceptance followed by a failed D1 mark remains an unresolved distributed boundary: the existing initial error/receipt-unconfirmed response and same-key recovery apply. This metadata change adds no automatic resend, queue, manual-review block or initial send state machine, and does not claim end-to-end exactly-once delivery. The manual PR14 reservation stays locked if its outcome transaction fails; accepted or ambiguous attempts never gain a new retry path. Definitive non-Fulfilled rejection still requires Preview retry and an explicit Send update. Fulfilled keeps its one-attempt rule.

No stage move, preview, sign-in recovery or metadata write sends email. Email availability stays independent of the website password gate. Website/admin authentication, CSRF, quotas, unpaid statuses, disabled payments and current retention controls remain intact. Local fixtures use synthetic responses and disposable SQLite data only. Actual provider capability, event reconciliation, mailbox delivery/reply and production migration/publication acceptance remain open under TECH03/EXT01.

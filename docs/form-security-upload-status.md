# Security feedback during an active upload

22 October 2026. Local fix prepared after CV-000010 completed successfully while checkout displayed an expired-security warning and an unusable retry control.

The Turnstile expiry/error callback correctly clears the token for a future attempt. The running private-upload submission already holds its initial verification and signed upload grant. The misleading state came from rendering security recovery feedback without checking whether the current submission was still busy.

`FormSecurity` now shows the recovery alert, separate sign-in guidance and Retry security check only when the service is idle and incomplete. The callback still clears the token and records its error. After a failed upload, the error/recovery controls become available normally; recovery keeps the original submission identity and requires an explicit subsequent submission. Challenge rendering, token validation, CSRF, signed grants, upload/finalization requests, timeouts, quotas, locks, payment state and email behavior are unchanged.

The new `tests/form-security-busy.browser.mjs` reuses the existing disconnected `form-recovery` fixture and real Checkout/FormSecurity components. A held single private upload reproduces the callback timing without repeating the live sixty-file test. Before the fix, the expiry case failed because the busy form contained one stopped-security alert. After the fix, all six combinations passed: expiry/error callback followed by success, HTTP 503 upload failure or HTTP 403 with expired sign-in. The success path finalizes once with the same order identity and grant; failures retain identity, keep submission disabled until a fresh security result, and never resubmit automatically.

The existing complete form-recovery browser journeys also passed, including configuration/script failure, expired/stale callbacks, separate sign-in, manual-review lock, uncertain request identity, private upload/resume memory, admin-preview restrictions and no browser storage writes.

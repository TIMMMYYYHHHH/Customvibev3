## Current provider capabilities

Cloudflare documents automatic D1 Time Travel, with 30 days on Workers Paid and 7 on Free. It restores a database in place and cancels in-flight queries. Bookmarks and an undo bookmark support recovery, while the documented facility currently does not clone a database to a new instance. This is documented availability, not a successful account restore or a recovery-time guarantee. A future scoped disposable provider exercise must use disposable data, verify the backend and record actual elapsed restore time. [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

D1 also documents SQL export/import. This preparation uses local SQLite snapshots, not a D1 export or Time Travel operation. Do not create longer-lived exports of private artwork/request data as a side effect of recovery preparation. [D1 import/export](https://developers.cloudflare.com/d1/best-practices/import-export-data/)

R2's compatibility table lists bucket versioning and replication APIs as unsupported. No deleted-object recovery guarantee is established here. Lifecycle deletion normally happens within 24 hours of expiry; application checks must deny access at the exact original deadline. Copying an object creates a fresh age for age-based lifecycle rules, so an age-only rule cannot preserve its original deadline after a restore. [R2 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [R2 lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)

These provider facts were checked against primary documentation on 19 October 2026. Account ownership and account-specific restore coverage remain unverified in this task.

The following approval-fence narrative records the historical rehearsal. Rerun the updated combined recovery fixtures before claiming current verification; retain capability isolation, immutable bytes, original expiry and no-send protections.


The fixture uses actual artwork, order and proof service functions against disposable SQLite and in-memory synthetic objects. A real SQLite backup file is reopened, and the content database is backed up separately. All outbound fetches throw. No production binding/configuration is loaded, no provider operation runs and no mail is sent. Temporary databases are deleted in a `finally` block; synthetic object copies die with the process. The retained evidence contains timings, source hashes and synthetic summaries, not customer records or secrets.

Seven synthetic orders exercise good, missing and corrupted files, artwork expiring during an outage, already-expired order details, a fulfilled order and a write after the snapshot. The restored snapshot has six orders; one expired order is removed, leaving five retained orders. One post-snapshot order is intentionally lost. A synthetic orphan object is removed. The snapshot is deliberately 120 seconds old at recovery, and the lost order was written 60 seconds after that snapshot. Those are engineered scenario values, not achieved production RPO.

The fixture records security snapshot creation, reopening both local snapshots, quarantine cleanup/reconciliation and total local restore-plus-verification timings. `snapshotMs` covers the security SQLite snapshot and object-map copy. No timing includes Cloudflare's restore service, object downloads, account recovery, human diagnosis, deployment, mail reconciliation or operational verification. Do not convert these small local timings into an RTO promise.

The checks demonstrate that a snapshot predating revocation can internally accept the old session before the recovery fence. The fixture then clears all proof sessions/capabilities, clears approvals, resets active orders to New, rotates a synthetic admin signing key, runs actual retention cleanup and reconciles each remaining object against its original manifest/hash/deadline. Missing/corrupt files are unfinalised and their orders require artwork preparation. A negative-control test omits the capability/approval fence and must fail. This sanitation is an explicit rehearsal procedure, not a claim that an unattended production restore already performs it.

Current fixture behavior, 21 October 2026: retired customer proof endpoints deny restored links and sessions immediately. Quarantine additionally clears legacy capabilities and sessions, rotates a synthetic admin key, runs retention cleanup and removes orphan or mismatched objects. It preserves valid historical approval audit and saved stages; neither creates customer approval requirements. Missing/corrupt artwork fails closed and requires internal preparation. The negative control detects omitted capability clearing. The emitted historical `sourceBaseline` identifies the fixture's earlier baseline, so record the actual tested revision and tree separately. Local fixture results do not verify live lifecycle settings or provider recovery.

The focused retention acceptance tests advance a controlled clock across the exact original fourteen-day boundary, retain whole-order notes through artwork reduction to six-calendar-month expiry, preserve completion expiry when reopening, and drain a cleanup backlog beyond one twenty-request batch. A failed object deletion must preserve the request and retained-byte quota for retry. These tests use disposable SQLite and synthetic objects with outbound requests denied.

## Order of operations for any future authorised recovery

1. Name the incident owner and record the outage start, suspected loss, reviewed release/schema and recovery source. Keep the website gate and separate admin sign-in enabled, payments disabled and provider writes paused during quarantine. Do not run an in-place production restore as a rehearsal.
2. Verify provider account access and the selected recovery point. Record current bookmarks, service versions and independently known revocations, replacements, sends, deletions and quota usage without collecting secrets. Preserve evidence of newer valid changes before choosing an older state. Use owner-controlled account recovery when required. A destructive production restore remains outside this preparation and requires separate concrete approval. Routine read-only or safely isolated disposable verification within approved allowances needs no extra approval solely because the provider account is live.
3. Recover only into an inaccessible quarantine. Inventory each request, order, revision and object. Retain original creation/artwork deadlines and six-month order-detail deadlines, including Fulfilled completion dates. Never run a historical retention migration merely to reset an old expiry or create a fresh 14-day window.
4. Invalidate historical proof capabilities/sessions conservatively where post-snapshot access decisions are unknown. Rotate the applicable website/proof and admin signing secrets through the authorised secret manager before allowing sessions. Do not rely on an old `revoked` table, restored cookies or an older approved flag. Preserve verified saved stages, fulfilled history and established detail expiry. Customer reapproval is not required. Reconcile replacement artwork through internal admin preparation, without creating review invitations.
5. Run `cleanOrders`/`cleanProofs` and `cleanArtwork` until no expired records or objects remain. The existing cleanup batches artwork requests in groups of 20 and order-artwork snapshots in groups of 50, so one invocation is not proof a large backlog is gone. Purge expired copies in every authorised recovery location before service resumes. Provider-managed history may contain prior state; never expose it by restoring stale private data without cleanup.
6. Reconcile every retained artwork reference with the original size, SHA-256, request ownership/parent relationship, current revision and original expiry. Exclude the separately managed derived locker snapshot from artwork orphan rules. Delete unreferenced artwork objects and detached proof/session metadata. Do not delete valid unfinished requests solely because they do not yet have an order. Missing or mismatched files fail closed; do not offer a complete ZIP or restore print eligibility. Preserve conservative service counters while reconciling current quotas.
7. Recover only unexpired, hash-matching files from an approved private source. An upload/copy must still be deleted at the original request deadline even though its object age restarts. Verify the application deadline, hourly cleanup and matching storage expiration policy before exposing it. No source may retain customer artwork or associated requests beyond the original deadline. If the file is expired or absent, it cannot be recovered from D1 metadata. Follow the owner-approved loss response and prepare replacement artwork internally when appropriate; never treat a historical approval as evidence for different bytes or require a new customer approval.
8. Verify current catalogue and seasonal rows, bindings, gates, secret presence, private bucket access, expiry rules and shared release revision. Reconcile external mail outcomes with the provider before a human uses Preview update / Send update. Restoring or moving an order must not send mail or imply payment, printing, a courier booking or dispatch. Sign-in recovery checks access only and does not replay writes.
9. Run the exact-artwork journey with disposable data and verify provider restore results in the scoped disposable environment. Record elapsed provider restore, total outage, reconciled/missing object counts and lost changes against approved DEC-04 targets. Record any unmet target, degraded service or customer action. Only the owner-approved acceptance can close final recovery work.

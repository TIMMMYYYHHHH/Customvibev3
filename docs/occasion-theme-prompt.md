# Reusable occasion theme brief

Replace the brackets before using this prompt.

Create an occasion theme for **[occasion name]** on CustomVibe. First inspect the current live customer website and the current source, project instructions and Founders Hub records. Use the latest implemented site as the baseline, including its current content, product photographs, collections, navigation, pricing and working flows. Preserve newer owner changes.

## Visual exploration first

Generate **five separate images showing five clearly different creative directions** for this occasion. Use the current homepage structure and recognisable navigation and actions. The visual treatment may change substantially, but visitors must not need to relearn how the site works. Keep the sections aligned with the existing site. Include a suitable occasion control in the navbar, optional editable seasonal wording, and tasteful decoration or motion ideas where appropriate. Do not invent discounts, delivery promises or product claims. Use original product photos accurately.

Label each direction clearly and explain its key idea briefly. Show the images and wait for me to choose or request revisions. Do not implement or publish a theme based only on the image-generation request.

## Scope and isolation

There is **one final theme per occasion**. Multiple image directions are explorations, not multiple installed themes.

**Theme only the customer-facing website. Do not redesign or seasonally style the admin centre, including Orders, Store content and Themes & seasons. Preserve the admin’s layout, navigation, typography, colours and controls. Only its embedded storefront preview should reflect the occasion. Reuse the existing admin settings and wording fields. If the approved design needs a new admin capability, explain that specific functional requirement before making that separate change.**

Keep theme assets, components and styles scoped to this occasion. Never replace the default website, overwrite another occasion or apply seasonal CSS globally to the admin or unrelated pages. Build on the shared current storefront, rather than maintaining a copied HTML website. Blank wording fields must inherit normal website wording. This draft must show draft wording immediately, even on the original design before a theme is installed. Website at selected date must follow actual eligibility and saved settings.

Preserve all current customer functionality, original photos, catalogue, pricing, studio tools, basket, checkout, contact flows, accessibility and responsive behaviour. Preserve the owner’s saved occasion icons, dates, recurrence rules, removals, drafts, wording, progress and schedule settings.

## After I select a direction

Refine the selected design and show how it extends to the relevant customer pages, desktop and mobile, before implementation. Once I approve the build, create a local working version using a checklist of existing sections and workflows so the implementation stays on brief. Test responsive layouts, keyboard use, reduced motion, visitor opt-out, wording fallback and isolation from other occasions. Honour the flat-control preference: no glowing or inset-shadow controls, no darker coloured border around a lighter matching fill with matching text. Never use em dashes or diagonal arrow icons.

Keep schedules off and do not mark Ready to use automatically. A theme can only activate when its approved design is installed, it is marked Ready to use, and its enabled schedule or confirmed manual override permits it. Use South African time and the existing activation confirmations and visitor preferences. Draft previews must never send real email or alter production customer records.

Keep Founders Hub tasks and subtasks current through its signed-in frontend, recording decisions and verified progress without duplicate tasks. Preserve the website password gate, separate admin authentication, disabled payments, privacy protections and free-tier limits.

Do not deploy or install the new theme in production until I explicitly approve that release. When approved, preserve the latest saved settings, publish paired website and admin preview builds from the same revision where shared storefront code changes, and verify the result. Deploying code must not automatically enable the occasion.

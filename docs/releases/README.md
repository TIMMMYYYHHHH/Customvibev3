# Release evidence

Store sanitized reviewed build, publication and compatibility records here through ordinary review. No automatic commit loop or invented historical baseline is allowed. Workflow artifacts expire after90 days; preserve required evidence before then.

A partial Pages receipt is not a verified paired release. Record real source/build/upload/current-version linkage, before IDs, pending components and explicit UNKNOWN/blocked fields. Keep original deployed private source when exact executable/config equality permits reuse. URLs and version labels do not authenticate provenance.

Publication uses manual exact-head dispatch. The completed historical manual M baseline is archived in `2026-10-20-release-M.json`, retaining Security's original source and the genuinely acknowledged Catalogue M source. A later tooling activation still needs new exact-source compiler facts and fresh private and schema evidence. Historical metadata review does not refresh actual observation times. See [release process](../release-process.md) for strict evidence fields, private-helper route, schema observation and synthetic rollback boundaries. Do not store secrets, binding dumps, customer data or raw provider logs.


Retrieve the real completed run and `release-manifest-<actual run ID>` artifact through established owner GitHub access before90-day expiry. Independently check run source/status, retain the actual downloaded manifest SHA256 and supply the reviewed `githubArtifact` handoff described in the release process. Do not invent run IDs, URLs, signatures, historical uploaded Functions bytes or a bootstrap JSON. Actual uploader fingerprints are distinct from source/compiler compatibility and provider readback facts.

Finish release M locally while main remains M, with required matching Admin through the unchanged helper, fresh metadata and all final identity readbacks. The pre-upload private snapshot gap remains explicit: drift may be detected after the Pages write and leave that attempt partial. Archive final sanitized provenance only afterwards through reviewed documentation revision N with its actual immutable URL when N exists. Manual-only publication prevents archive pushes from recursively deploying. The existing historical M archive does not certify any later activation.


For the next manual dispatch, only one newly added committed `YYYY-MM-DD-release-<label>.json` may accompany the fixed tooling paths. Supply its exact reviewed file hash/path, original completed source M and candidate N through `archivedRelease`; the coordinator checks the complete original receipts, final protections/readbacks, committed regular-file bytes and absence of a future-N self-reference. Historical unknown Functions bytes remain absent/null. This exception does not allow arbitrary JSON or modification of an existing immutable record. See the release process for the exact input fields. The original M record stays unchanged while the external reviewed input envelope may cite its real N archive URL once N exists.

Automated records preserve three distinct phases: original observations, the runner's synchronous authorization immediately before uploader invocation, and fresh final verification. The original 600-second freshness limit remains mandatory at invocation and at the later of invocation or returned provider creation time. Later successful completion does not replace those timestamps. Provider creation, caller invocation and runner acknowledgement receipt are separate facts; none claims an observed internal HTTP POST clock.

An automated archive requires the actual run attempt, bounded `prewriteValidation`, linked attempt and acknowledgement clocks, original upload proof and separate `completionEvidence`. Current completion evidence includes a genuine fresh staged review with the unchanged original rollback object. The original evidence and successful artifact remain retained. Missing clocks do not downgrade an automated record into the historical manual M format. That genuine manual record remains unchanged with null historical Functions proof.

Keep the original downloaded ZIP and member bytes outside the mutable working record, with their hashes and actual same-attempt run, artifact, job and publishing-step context. These hashes bind reviewed content; authorised GitHub retrieval supplies origin. Only completed successful artifacts qualify. Failed or uncertain writes and sticky local failures remain partial and require separate recovery review. Never erase them by replacing the working copy with an older artifact. The CLI enforces sticky reasons in retained records; external replacement of all history cannot be detected without an independent ledger. See the release process for the exact positive handoff fields and clock bounds. No private support files, schema DDL, customer rows, secrets or raw logs belong in an archive.
